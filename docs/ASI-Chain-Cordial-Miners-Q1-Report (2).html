02BLOCKLACE

A local view,
not a global chain

A blocklace is a local directed acyclic graph of blocks not a single global chain. Each block can reference multiple predecessors, letting a node represent partial knowledge of the network exactly as it is seen.

EVERY NODE SEES A DIFFERENT SLICE OF THE SAME TRUTH

03WHY GO BEYOND A CHAIN

The blocklace shift

TRADITIONAL BLOCKCHAIN
Single linear chain
Classical blockchains force one global chain at block‑creation time a serialized path that becomes a massive bottleneck as the network grows.
BLOCKLACE / DAG
Partially ordered DAG
Nodes grow a partially ordered, multi‑parent DAG first removing the serialization bottleneck then derive consistent ordering later, under explicit safety and finality rules.

08IMPLEMENTATION

How we implemented detection and exclusion

The implementation treats equivocation as a local DAG fact. We detect conflicting creator histories already present in the blocklace, reject new conflicting insertions, and exclude equivocators from approval, tip selection, fork choice, and safe dissemination.

01
Detect same-round conflicts
creator_blocks_at_round, equivocation_blocks_at_round, and all_equivocations scan the local blocklace by creator and round to surface conflicting branches.
02
Reject insertion and hidden branches
validate_block enforces the chain axiom against incomparable creator histories, and strict validation also rejects HiddenEquivocation when a candidate acknowledges only part of a known conflict.
03
Exclude from support and fork views
approves(...) returns false when an approver observes a conflicting sibling, while collect_validator_tips and fork_choice filter out validators marked as equivocators.
04
Disseminate safely and keep proof
select_predecessors starts from honest visible tips, then adds missing known equivocation branches so new blocks do not hide them, while the evidence pool retains conflicting blocks for later slashing proof.

16DURABILITY

Persistence and recovery

The current implementation persists Cordial blocks and finalized progress to LMDB, then rebuilds the in-memory Blocklace on startup. This slide describes the storage and recovery path that exists today.

M
In‑Memory Engine
The live consensus Blocklace still runs in memory during normal operation.
D
Durable Block Store
Validated blocks are written to an LMDB-backed repository before insertion into the engine.
P
Persisted Finality Cursor
The latest finalized block identity is stored as the restart resume point.
R
Restart Replay
On startup, persisted blocks are replayed in topological order back into Blocklace.

Implemented here: persistent block storage, finalized cursor continuity, and deterministic boot recovery. Not claimed here: a fully disk-native consensus engine.
