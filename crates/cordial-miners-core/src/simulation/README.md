# Simulation Module

This folder contains simulation-oriented support for the Cordial Miners core.
The goal of this module is to let us exercise dissemination, finality, and
ordering behavior in a controlled environment before wiring everything into a
live integration path.

## What is here

### `dissemination.rs`

This file contains the lightweight simulation harness used for protocol-level
behavior checks.

It provides:

- `SimNode`
  - a local blocklace view
  - a pending buffer for out-of-order blocks
  - helper methods for local proposal construction, final leader lookup, and tau output
- `SimNetwork`
  - a minimal message delivery queue
  - explicit control over delivery order
  - replay support for buffering and retry behavior

This is the module used by the dissemination and convergence tests.

### `trace.rs`

This file exports simulation state into a frontend-friendly trace format.

It provides:

- block metadata for the visualized wave
- timeline events such as delivery, partition, and heal
- per-step node snapshots
  - known blocks
  - buffered blocks
  - partition status
  - final leader
  - local tau output

The current exported scenario is the 4-node convergence demonstration used to
show that different local delivery orders can still converge on the same final
leader and the same tau output.

## 4-node convergence demonstration

The current simulation trace models a single honest wave in a 4-validator
setting with:

- one observer receiving blocks in dependency order
- one observer receiving blocks out of order and buffering missing dependencies
- one observer being partitioned and later healed
- one observer receiving a different but still valid sequence

The expected result is:

- all observers eventually know the same wave blocks
- all observers eventually finalize the same leader block
- all observers eventually compute the same local tau output

This scenario is backed by the test:

- [test_four_node_convergence.rs](/home/john/Desktop/rust/blocklace/crates/cordial-miners-core/tests/test_four_node_convergence.rs)

## How to generate the trace

The trace is not written from a test file. Instead, it is generated by a small
binary so that running tests does not create files.

Run this from the repository root:

```bash
cargo run -p cordial-miners-core --bin export_four_node_trace
```

This writes the generated trace to:

```text
docs/cordial-miners/generated/four-node-trace.js
```

That generated folder is intentionally git-ignored.

## How to view the simulation

After generating the trace, open:

- [four-node-convergence-visualizer.html](/home/john/Desktop/rust/blocklace/docs/cordial-miners/four-node-convergence-visualizer.html)

The visualizer reads the generated trace file and renders:

- the wave blocks
- the replay timeline
- buffering and catch-up behavior
- per-observer local state
- final leader convergence
- tau output convergence

## Why this exists

This simulation layer gives us three benefits:

- protocol validation
  - we can test convergence behavior without needing the full live node stack
- explanation
  - we can demonstrate adversarial or delayed-delivery behavior visually
- integration readiness
  - we can move from protocol proofs toward live system wiring with clearer intermediate artifacts

## Current scope

Right now the visualized/exported scenario is a single 4-node convergence case.
This can be extended later with additional traces for:

- equivocation attempts
- partition-and-heal variations
- weighted finality and weighted tau
- stronger multi-wave scenarios

The intended design is:

- Rust remains the source of truth for the simulation
- generated traces are the interchange format
- the frontend remains a renderer rather than a second protocol implementation
